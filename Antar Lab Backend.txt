Antar Lab Backend Architecture and Execution Blueprint: High-Throughput Police AI Systems with Off-Device LLM Inference
1. System Architecture, Initialization Lifecycle, and Request Stack
1.1 Launcher Mechanics, Pre-Import Resource Constraints, and Thread Isolation
The Antar Lab backend architecture executes all analytical workflows, spatial-temporal modeling, vector search operations, and data transformations locally on host hardware while delegating natural language generation exclusively to the QuickLLM API. System launch originates in run.py, which executes log_capacity() to inspect Linux cgroup constraints (/sys/fs/cgroup/memory.max) and system Resident Set Size (RSS) via psutil. This memory inspection ensures container limits are logged immediately upon boot. Bind port resolution follows a strict priority chain (X_ZOHO_CATALYST_LISTEN_PORT 
→ PORT 
→ APP_PORT 
→ 8000), invoking Uvicorn with single-worker execution (workers=1) to prevent process-level memory fragmentation and state divergence across local workers.   

Prior to loading FastAPI or application modules, main.py enforces runtime isolation policies:   

Standard output and standard error streams (sys.stdout, sys.stderr) are reconfigured to utf-8 encoding to prevent UnicodeEncodeError exceptions during high-frequency logging of Kannada text strings.   

Offline environment variables (HF_HUB_OFFLINE=1, TRANSFORMERS_OFFLINE=1) are asserted, preventing runtime network polling to external HuggingFace repositories.   

Basic Linear Algebra Subprograms (BLAS) thread contention is capped by setting OMP_NUM_THREADS=1, MKL_NUM_THREADS=1, and OPENBLAS_NUM_THREADS=1.   

A strict DLL import sequence is enforced by importing onnxruntime prior to scikit-learn or scipy. This ordering ensures ONNX Runtime initializes its OpenMP runtime cleanly, avoiding C-level OpenMP DLL collisions and kernel panics under Windows and Linux environments.   

1.2 Lifespan Mechanics and Asynchronous Background Warmup
Application initialization uses FastAPI’s lifespan context manager, bifurcating startup into a sub-second synchronous core boot phase and a non-blocking asynchronous background task (background_warmup()):   

The synchronous boot sequence completes in under one second. The routine db_path.ensure_db_staged() resolves database bindings. In Lab edition (ANTAR_EDITION=lab), the backend connects directly to D:\Project\main_lab.db (~19 lakh FIR records) with Write-Ahead Logging (WAL) mode enabled and a 2 GB memory-mapped I/O (mmap) allocation. The application then initializes the cryptographic hash-chained audit_log database (audit_store.init_db()), hydrates officer interaction memory (init_memory_db()), parses agent manifests from AGENTS.md via register_default_fleet(), and verifies agent code integrity using agent_lock.enforce().   

The asynchronous warmup task executes via asyncio.create_task(), allowing GET /api/health to respond immediately to load balancer health checks. In the background, zcql_local.ensure_indexes() builds covering SQLite composite indexes and verifies the normalized crimes SQL view. The warmup task loads the ONNX bge-small-en-v1.5 embedding model and the ms-marco-MiniLM-L-6-v2 cross-encoder (onnx_backend.py), populates the curated vector index (brain_vectors.db containing 100,000 8-bit quantized int8 vectors), hydrates district lookup caches and co-accused subgraphs, and starts the autonomous Sentinel watch loop (orchestrator.start_autonomous()).   

1.3 Middleware Pipeline Execution Order
HTTP request processing follows a reverse-registration Starlette/FastAPI middleware pipeline where outermost wrappers execute first:   

security.py: Enforces HTTP request body limits (ANTAR_MAX_BODY_MB = 10), injects security headers (X-Content-Type-Options: nosniff, X-Frame-Options: DENY), and scrubs stack traces from unhandled exceptions, mapping them to public tracking identifiers (ERR-<10HEX>).   

CORSMiddleware: Validates cross-origin request headers against explicit origin allowlists.   

GZipMiddleware: Applies GZip compression to non-streaming HTTP responses exceeding 500 bytes while bypassing Server-Sent Events (/api/chat/stream) and binary voice streams.   

obs_middleware: Injects a unique X-Request-ID, initiates monotonic latency tracking, and records request metrics to data/obs/obs.db.   

auth_middleware: Decodes HMAC-SHA256 Bearer tokens or request headers (X-Role, X-Officer), evaluates token revocation states via revocation.is_revoked(), and binds an immutable SecurityContext containing user role and officer ID.   

audit_middleware: Intercepts state-mutating requests, extracting execution parameters for inclusion in the tamper-evident audit ledger.

2. Data Engineering and Database Scaling to 19+ Lakh Records
2.1 Ingestion Pipeline, Signature De-duplication, and Canonical Cleaners
Expanding the primary operational database (main_lab.db) from 10 lakh to 19+ lakh real FIR records requires ingesting the raw extract file E:\Datathon_2026\03_resources\FIR_Details_Data.csv (573 MB, 1,674,734 records spanning January 2016 through March 2024). 2.2 SCRB Official ER Schema Alignment and Zero-PII Compliance
To align with official State Crime Records Bureau (SCRB) schema requirements while preserving compatibility with existing SQL queries on the primary FIRs table, scripts/lab/build_er_tables.py generates normalized relational tables alongside the primary entity store.   

The normalized schema establishes clear relational connections across entities:

District acts as a primary geographical master table, maintaining a 1:N relationship with Unit (police stations).   

Unit maintains a 1:N relationship with CaseMaster, which serves as the core case entity. CaseMasterID maps 1:1 to FIRs.id and stores an official 18-digit normalized key (CrimeNoOfficial). CaseMaster links via foreign keys to District, Unit, CaseStatusMaster, and CrimeHead.   

CaseMaster maintains 1:N relationships with ActSectionAssociation (storing parsed statutory acts and sections) and CaseInvestigatingOfficer (linking investigating officers by employee ID). It also links 1:1 to aggregate demographic counts in arrest_counts and case_person_counts.   

The official SCRB extract provides aggregated demographic tallies without individual citizen PII. Tables required by the ER model (Accused, Victim, ComplainantDetails) are instantiated with full column schemas but maintained at 0 rows. Demographic metrics are tracked in aggregate tables (case_person_counts, arrest_counts), and an audit view (er_fill_rates) records data completeness percentages to maintain structural compliance without introducing synthetic PII data.   

2.3 Storage Tiering: Transactional SQLite WAL vs. Analytical Parquet & DuckDB
To support low-latency point lookups alongside analytical aggregations over multi-million row datasets, the system uses a dual-engine storage architecture:   

Point lookups, single-case queries, graph traversals, and transactional updates execute against the SQLite transactional tier (main_lab.db). The engine operates with 30 composite covering indexes (including idx_firs_group_date, idx_firs_u_zone_status, and ix_forecast_cube_unit). Memory mapping (PRAGMA mmap_size=2147483648) enables read queries to access the OS page cache directly, reducing user-space memory copying overhead.   

Complex multi-year trend aggregations, group-by analytics, and benchmark workloads execute against the DuckDB analytical tier (scale_bench.py). The analytical dataset is exported via export_parquet.py into ZSTD-compressed columnar Parquet files (scale/firs_lab.parquet) with dictionary encoding on low-cardinality text fields (district_norm, crime_type, status). DuckDB queries these files using vectorization and multi-threading (PRAGMA threads=10).   

To evaluate performance at higher scale, make_stress.py samples the Parquet dataset with replacement to build a 10,00,000-row synthetic stress dataset (scale/firs_stress_1cr/*.parquet, ~2.1 GB across 10 row groups). This dataset powers live latency comparisons between SQLite and DuckDB during scale demonstrations.   

3. Hybrid RAG Architecture and Bilingual Kannada NLP Bridge
3.1 Dense-Sparse Retrieval and Reciprocal Rank Fusion
Search over unstructured modus operandi (MO) text and case narratives relies on a hybrid retrieval architecture. Dense vector search and sparse lexical BM25 retrieval execute concurrently, combining output rankings via Reciprocal Rank Fusion (RRF):   

The hybrid retrieval process operates across four sequential steps:

Dense Retrieval: Input queries are embedded locally via an ONNX-quantized bge-small-en-v1.5 model, producing 384-dimensional dense vectors. The vector engine evaluates cosine similarity against 100,000 int8 vectors stored in brain_vectors.db, returning the top candidate matches.   

Sparse Lexical Retrieval: BM25 evaluates exact keyword matches across Crime Group, Crime Head, Act Sections, and MO Details fields, returning top lexical candidate matches.   

Reciprocal Rank Fusion (RRF): Because vector cosine distances and BM25 relevance scores follow different numeric distributions, combining raw scores can introduce bias toward one retriever. RRF merges candidate rank positions directly without score normalization:

A final Maximal Marginal Relevance (MMR) selection step de-duplicates semantically redundant results, maximizing information diversity within the final context window.

Kannada language queries are processed through a deterministic NLP pipeline before intent contexts are passed to the QuickLLM API:   

Query execution follows a structured five-stage translation and isolation pipeline:

Lexicon Bridge Mapping: The module kn_bridge translates extracted root terms into standardized English entities present in the official KSP database. For instance, "ಮೈಸೂರು ನಗರ" maps to "Mysuru City", while "ಕಳ್ಳತನ" maps to the Crime Group "THEFT".   

SQL Template Compilation: Standardized entity terms are passed to query_agent.py, which selects pre-compiled parameterized SQL templates (e.g., Template T1 count aggregation). SQL execution runs entirely against the local database (main_lab.db).   

LLM Generation Isolation: The resulting SQL aggregate data, query intent, and non-sensitive context are passed to the QuickLLM API. QuickLLM generates the final natural language response in Kannada without directly querying the database or receiving citizen PII.

6. Empirical Benchmark Harness and Live Demonstration Strategies
6.1 Deterministic Gold Question Benchmark Harness
System accuracy is evaluated using scripts/eval_gold.py against a 150-item gold standard benchmark set (docs/gold/gold_questions.jsonl, consisting of 75 query pairs in English and Kannada).   

The benchmark dataset covers 11 query categories: Count scalar lookups (10), Spatial rankings (12), Multi-year trends (8), Anomaly spikes (8), Disposal rates (6), Specific case lookups (8), Entity link graphs (4), Aggregate demographics (4), Data gap identification (5), Policy refusal enforcement (5), and Relative temporal windows (5).   

Evaluation accuracy is measured using BIRD-style result set matching, evaluating output values against ground-truth SQL executed directly on main_lab.db. Numerical correctness is checked using extract_numbers(), which parses numbers from output text (normalizing Indian grouping like 1,23,456, Western formatting, percentages, and scale terms like lakh or crore). Parsed numbers are cross-referenced against SQL outputs and citation metadata. Any number in the generated answer that cannot be derived from retrieved data fails verification, tracking the unsupported calculation rate.

6.3 Live Demonstration Strategies
Demonstration impact is optimized through four technical capabilities:   

Temporal Lock Synchronization (ANTAR_TODAY=real): System temporal evaluation is locked to March 31, 2024 (the final date of historical records in the official extract). This prevents post-dated test data from distorting historical spatial trends or temporal comparisons.   

Dynamic Role Switching (OfficerSelector UI): The client UI enables switching active permissions between Constable, Inspector, and Approver ranks. This visualizes RBAC enforcement, demonstrating how restricted endpoints (such as suspect profiling or network graphs) control access based on officer rank.   

Visual Model Explanations ("Why" Drawer): The Predict interface highlights exact TreeSHAP driver attributions generated by the LightGBM Challenger model. Selecting a spatial unit displays multiplicative risk drivers (e.g., 
+24% volume from 4-week trend, 
+12% seasonal alignment), presenting model outputs as clear operational rationale.   

Audited Falsification Demonstration: Demonstrators can trigger an HTTP 409 Conflict by attempting to confirm an unverified suspect link. The UI displays the AI's Bayesian rebuttal alongside Popperian falsifiers, demonstrating the audited override path required to confirm the association.   

7. Strategic Implementation Roadmap
System deployment and validation proceed across eight execution phases:

Phase L0: Environment Setup and Isolation: Install core packages (lightgbm, duckdb, pyarrow, locust) into D:\Project\.venv. Create the disposable database copy main_lab.db from main.db, configure .env.lab.example, and verify initial startup parameters.   

Phase L1: Data Top-Up and Ingestion: Execute topup_firs.py to ingest historical FIR records from the extract file, expanding main_lab.db to ~19 lakh rows. Apply signature deduplication, stage normalization, regex section parsing, and rebuild dependent vector and forecast caches.   

Phase L1b: System Clock Synchronization: Implement app/core/clock.py to manage system temporal boundaries. Replace date.today() calls across query paths with clock.today(), binding temporal queries to the historical data boundary (March 31, 2024).   

Phase L2: Official SCRB ER Schema Normalization: Execute build_er_tables.py to construct normalized relational tables (CaseMaster, ActSectionAssociation, CaseInvestigatingOfficer) alongside FIRs. Populate foreign key relationships and instantiate aggregate demographic tables to maintain zero-PII compliance.   

Phase L3: Forecasting Model League: Implement forecast/challenger.py using LightGBM Poisson regression. Integrate TreeSHAP driver extraction, top-down spatial reconciliation, and Mondrian split-conformal prediction bands. Build forecast/league.py to evaluate Champion GLM vs. Challenger LightGBM models using PAI and PEI metrics.   

Phase L4: Gold Benchmark Harness Implementation: Author 150 bilingual benchmark questions (docs/gold/gold_questions.jsonl) spanning 11 query categories. Implement eval_gold.py to score execution accuracy against ground-truth SQL and verify zero-hallucination numerical output using extract_numbers().   

Phase L5: Scale Benchmarking and Parquet Export: Export dataset records to ZSTD-compressed Parquet (export_parquet.py) and generate the 1-crore row stress dataset (make_stress.py). Build scale_bench.py to evaluate query latency across SQLite and DuckDB engines, and execute Locust multi-user load tests.   

Phase L6 & L7: Frontend UI Integration and Demo Rehearsal: Mount Lab UI components (Predict Model League, Accuracy Card, Scale Benchmark Page, Schema Panel) conditionally based on backend edition health flags. Rehearse live demonstration workflows under timed conditions to ensure latency and UI stability.   

8. Architectural Conclusion
The Antar Lab backend architecture demonstrates that high-throughput police intelligence systems can run effectively on local hardware by pairing local data processing engines with off-device LLM inference APIs. Offloading language generation to QuickLLM while executing database operations, vector retrieval, spatial-temporal forecasting, and cryptographic auditing locally maintains fast query response times, operational data privacy, and rigorous analytical performance.
