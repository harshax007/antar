## 1. What "done" means

Antar Lab is the **same codebase** as Antar Cloud, switched by settings, running on the
owner's laptop with:

1. **~19 lakh FIRs** in `main_lab.db`: the current 10 lakh plus the unused real rows from the
   official extract, cleaned, de-duplicated and loaded insert-only (L1).
2. **"Today" = the end of the real record** (≈ 31 Mar 2024) for every answer, map and forecast,
   so nothing seeded after that date is counted (L1b).
3. **The official ER design**, implemented as real tables derived from the extract, with
   person tables honestly empty, and a schema view with fill rates (L2).
4. **Champion vs challenger forecasting**: the existing Poisson GLM vs a new LightGBM model,
   scored on held-out real weeks with MAE, deviance, band coverage, capture, PAI and PEI, and
   shown as a league table with predicted-vs-actual and a per-forecast "why" (L3).
5. **A 150-item gold question set** (75 questions × English and Kannada) with hand-written
   ground-truth SQL, scored by a harness for execution accuracy, plus a no-hallucinated-number
   rate, published as `docs/ACCURACY.md` and an Accuracy card (L4).
6. **Scale you can watch**: Parquet export, a 1-crore stress copy, DuckDB vs SQLite timings on
   six fixed queries in a new Scale page, and a Locust concurrency run (L5).
7. **Frontend**: Lab-only Predict league table, Accuracy card, Scale page and Schema panel,
   appearing only when the backend says it is the Lab edition (L6).
8. **Rehearsed**: the demo script in `docs/DATATHON_FINAL_PLAN.md` §7 runs clean twice on the
   Lab (L7).

Priority order if time runs short: **L0 → L1 → L1b → L4 → L3 → L5 → L2 → L6 polish → L7**.
L4 and L3 carry the two strongest claims; L2 is the cheapest to cut.

## 4. Phase L1: top up to ~19 lakh real FIRs (≈ 2 h, mostly unattended)

### L1.1 New module `app/services/fir_clean.py` (pure functions, unit-tested)

Everything here is deterministic and has no DB access, so it can be tested in isolation.

**a) Stage mapping** `canonical_stage(raw: str) -> tuple[str, int | None]`

- Map the raw `FIR_Stage` (343 spellings) to one of the 13 `CaseStatusMaster` names and its ID.
  Rule order: exact match (case-insensitive, whitespace-collapsed) → a hand-written alias
  table (e.g. `"Dis / Acq"`, `"Dis-Acq"`, `"Acquitted"`, `"Discharged"` → `Dis/Acq`;
  `"Pending trial"`, `"PT"` → `Pending Trial`; `"UI"`, `"U.I"` → `Under Investigation`;
  `"Bound Over"` → `BoundOver`; `"Untraced"` → `Un Traced`) → `difflib.get_close_matches`
  with cutoff 0.85 → `("Other Disposal", 15)` with the raw value kept.
- **Build the alias table from data, not guesses:** first run
  `SELECT FIR_Stage, COUNT(*) FROM <csv> GROUP BY 1 ORDER BY 2 DESC` in pandas, print all 343,
  and write the aliases for every spelling with ≥ 50 rows. Store the table as a dict constant
  with a comment giving the count each alias covers.
- The FIRs row keeps the **raw** stage in `FIR_Stage` and `status` (as `K` rows do). The
  canonical value goes into the ER table `CaseMaster` (§5).

**b) ActSection parser** `parse_act_section(raw: str) -> list[dict]`

The raw text is a sequence of `<ACT NAME> U/s: <sections>` groups, e.g.
`PROTECTION OF CHILDREN FROM SEXUAL OFFENCES ACT 2012 U/s: 12 IPC 1860 U/s: 306,363 PROTECTION
OF CHILDREN FROM SEXUAL OFFENCES ACT 2012 U/s: 18`. Algorithm:

1. Split on the literal `U/s:` (case-insensitive). Piece 0 is the first act name. For each
   later piece `p`, the sections are the leading run matching
   `^\s*([0-9A-Za-z()/.\-]+(?:\s*,\s*[0-9A-Za-z()/.\-]+)*)`; whatever follows is the next act
   name.
2. Normalise each act name: upper-case, collapse spaces, strip trailing commas, then map to an
   `Act.ActCode` (138 rows) by exact match, then by `difflib` (cutoff 0.8) against
   `ActDescription`. Unmatched names are kept as raw text with `act_code = None`.
3. Split sections on commas; trim; keep sub-clauses (`304(A)`, `78(3)`).
4. Return `[{"order": i, "act_raw": …, "act_code": …, "section": …}]`, preserving order
   (the first act is the principal one).

Required unit tests (`tests/test_fir_clean.py`, new) with the three sample rows from the CSV
head and the two `K` rows in §2.3: section lists, act order, `304(A)` kept, and the POCSO act
appearing twice in one row parsed as two groups. Measure the parse rate over the whole CSV and
assert ≥ 99.5% of non-empty values yield ≥ 1 group (the source plan measured 99.8%).

**c) Coordinates** `clean_coords(lat, lon) -> tuple[float|None, float|None, str]`

Returns cleaned values and a reason: `ok`, `swapped` (lat/lon reversed but valid), `outside`
(not in the box 11.5–18.5 N, 74.0–78.6 E, same as `fir_upload.LAT_MIN…`), `missing`. Used only
for the side table `fir_geo_clean` and the load report. The FIRs row keeps raw values (§2.3).

**d) Signature** `signature(row: Mapping) -> str`

The de-duplication key. Use these **13 fields**, all normalised with `str(v).strip().upper()`
and integers with `int(float(v))` (empty → ""):

`District_Name, UnitName, FIR_YEAR, FIR_MONTH, FIR_Day, FIR_Type, CrimeGroup_Name,
CrimeHead_Name, KGID, Beat_Name, Village_Area_Name, Accused_Count, Place_of_Offence`

Return `sha1("|".join(fields))`. **Do not include `ActSection`** (the `C` rows store a
rewritten form, so it would never match) or `FIR_Stage` (stages change over time). Note that the
18 Sep load used a 14-field signature whose exact definition was not saved; this one is
documented here and in the script, and its collision behaviour is measured in L1.2 step 3.

### L1.2 New script `scripts/lab/topup_firs.py`

Command line:

```
--csv E:\Datathon_2026\03_resources\FIR_Details_Data.csv
--db  main_lab.db          (refuses main.db unless --i-know)
--dry-run                  (default ON; --apply to write)
--limit N                  (optional, for a quick trial)
--batch 50000
```

Steps:

1. **Read the CSV** with pandas, `dtype=str`, `keep_default_na=False`, `encoding="utf-8"`
   (fall back to `latin-1` with a warning). Rename columns to the DB names using the same map
   as `fir_upload._DB_NAME` (spaces, tabs and dots → `_`; `Arrested Count\tNo.` →
   `Arrested_Count_No_`). Drop `Offence_Duration` (not a FIRs column).
2. **De-duplicate inside the extract**: drop exact duplicate rows (expected ≈ 22,791), then
   drop rows whose `signature` repeats (keep first). Print both counts.
3. **De-duplicate against the register**: stream
   `SELECT <13 fields> FROM FIRs WHERE is_synthetic_row = 0` from `main_lab.db`, compute
   signatures, build a Python `set` (≈ 9.5 lakh × 40 bytes; fine in 32 GB). Drop extract rows
   whose signature is in the set. **Also report** how many existing `K` rows matched an extract
   row (should be ≈ 5,75,000; if it is far lower, the signature disagrees with how `K` rows were
   stored: stop and investigate before applying).
4. **Keep only rows that pass**: non-empty `District_Name`, `UnitName`, `CrimeGroup_Name`; a
   valid date from `FIR_YEAR/FIR_MONTH/FIR_Day` (`datetime.date` succeeds); date between
   2016-01-01 and 2024-03-31. Count each refusal reason.
5. **Assign ids**: `start = max(SELECT MAX(id) FROM FIRs, max id in upload_rows if that table

### L1b.1 New `app/core/clock.py`

```python
"""One "today" for the whole app.

ANTAR_TODAY = wallclock   (default) the calendar date in IST
            = real        the last date of the real KSP record in the register
            = YYYY-MM-DD  a fixed date (Lab demo, tests)
"""
import os
from datetime import date, datetime, timedelta, timezone
from functools import lru_cache

_IST = timezone(timedelta(hours=5, minutes=30))

def _spec() -> str:
    return (os.getenv("ANTAR_TODAY") or "wallclock").strip().lower()

@lru_cache(maxsize=1)
def _real_end() -> date | None:
    from app.core.db_path import DB_PATH, registry_connect
    con = registry_connect(f"file:{DB_PATH}?mode=ro", uri=True)
    try:
        top = con.execute("SELECT MAX(date) FROM FIRs WHERE is_synthetic_row = 0").fetchone()[0]
    finally:
        con.close()
    return date.fromisoformat(str(top)[:10]) if top else None

def today() -> date:
    s = _spec()
    if s in ("", "wallclock", "today", "now"):
        return datetime.now(_IST).date()
    if s == "real":
        return _real_end() or datetime.now(_IST).date()
    return date.fromisoformat(s)

def is_fixed() -> bool:
    return _spec() not in ("", "wallclock", "today", "now")
```

Default behaviour is unchanged (wall clock), so the Cloud build is unaffected.

### L3.1 New `app/forecast/challenger.py` (LightGBM global model)

Interface mirrors `model.fit` / `model.predict` so the back-test can treat both alike:

```python
@dataclass
class LgbFit:
    horizon_days: int
    booster: "lightgbm.Booster"
    feature_names: list[str]
    alpha: float                 # NB2 dispersion from training residuals (reuse model._dispersion)
    conformal: dict              # reuse model._calibrate on a held-out block
    trained_rows: int
    seconds: float

def fit(p: Panel, last_origin: int, horizon_days: int, *, n_cal_origins=8,
        max_train_origins=60, max_rows=400_000, seed=0) -> LgbFit: ...

def predict(p: Panel, f: LgbFit, t: int, *, explain: bool = False) -> dict[str, np.ndarray]:
    # returns the same keys as model.predict: expected, lo80, hi80, lo90, hi90,
    # baseline, ewma, seasonal_naive, recent4, usual_level (+ contrib when explain=True)
```

Design decisions (fixed, so results are comparable and reproducible):

- **Training rows**: identical origin selection to `model.fit` (use `model._valid_origins`,
  hold out the last `n_cal_origins` for calibration, cap `max_train_origins`), but the feature
  matrix is built by a new `_lgb_rows(p, origins, h)` that takes the dict from
  `features.features(p, t, h)` and stacks these columns per unit:
  `last1, last4, last13, usual, last_year, nbr4, nbr1, nbr_usual, area, area_usual, ewma`,
  `sin(ang), cos(ang), sin(2·ang), cos(2·ang)`, `log1p(usual)`, the unit's parent index as a
  **categorical** feature (`p.units.parent_of`), and `unit_type` constant. Same row filter as
  `model._rows` (units with any signal).
- **Target / objective**: `y = p.target(t, h)` (counts over the horizon), `objective="poisson"`,
  and pass `init_score = log(exposure(f, h))` (the same base rate the GLM uses as offset),
  so LightGBM learns adjustments to the usual level, exactly like the GLM. Without
  `init_score` it has to learn the level too and loses on sparse beats.
- **Hyper-parameters** (no tuning on the scored window; R13): `num_leaves=63,
  learning_rate=0.05, n_estimators=600, min_data_in_leaf=200, feature_fraction=0.8,
  bagging_fraction=0.8, bagging_freq=1, lambda_l2=1.0, verbose=-1, num_threads=10,
  seed=seed, deterministic=True`. Early stopping on the calibration block's Poisson deviance
  (patience 50). Record the best iteration.
- **Bands**: compute `alpha = model._dispersion(y_cal, mu_cal)` and
  `conformal = model._calibrate(y_cal, mu_cal, alpha)`, then `model.bands(mu, alpha, conformal,
  level)` for 0.8 and 0.9. This gives the challenger the same Mondrian split-conformal bands as
  the champion (Pearson residuals per volume bin), which is the method the 2025 Tweedie/LightGBM
  conformal study found best calibrated (arXiv 2507.06921).
- **Beats**: fit the beat challenger on beats directly (global model), then apply the same
  top-down reconciliation as the champion (`model.reconcile` with the **champion's** station
  parent) so beat totals stay coherent. Record whether reconciliation was applied.
- **Why (explain=True)**: `booster.predict(X, pred_contrib=True)` gives exact TreeSHAP
  contributions per feature in log space (no `shap` package needed). Convert to multipliers
  (`exp(contrib)`) and group them into the GLM's driver groups (`features.DRIVER_GROUPS`:
  level, recent, last year, neighbours, area, season) so both models explain in the same words.
- Guard: if `lightgbm` is not importable, `fit` raises `ChallengerUnavailable`, and the
  back-test records the challenger as "not run" instead of failing.

### L5.3 Benchmark service `app/services/scale_bench.py` (new) and API

Six fixed queries, each written **twice** (SQLite on `main_lab.db` `FIRs`; DuckDB on the
Parquet). Keep them equivalent (same filters, real rows only where the app does):

| # | Name | What |
|---|---|---|
| Q1 | District ranking | `COUNT(*)` by district, descending, top 10 |
| Q2 | Monthly trend | count by `YYYY-MM` across all years |
| Q3 | Crime mix per station | count by station × crime_type, top 50 |
| Q4 | Pendency | share `Under Investigation` by district, cases older than 90 days as of `clock.today()` |
| Q5 | Day of week | count by weekday for one crime type statewide |
| Q6 | 2-key join | FIRs ⋈ (district, year) totals (self-join via CTE), share of each district-year in its year |

- `run(engine, dataset, query_id) -> {rows, ms, engine, dataset, n_rows_scanned}`; engines
  `sqlite` (19 lakh), `duckdb` (19 lakh Parquet), `duckdb` (1 crore). Warm each once; report
  the median of 3 runs and the first (cold) run separately. DuckDB: one connection per process,
  `PRAGMA threads=10`, read with `read_parquet('…/*.parquet')`.
- Check equivalence: SQLite and DuckDB on the same 19-lakh data must return identical results
  for each query (a test asserts it).
- API (new router `app/api/scale_api.py`, Lab only; return 404 with a clear message when
  `not is_lab()`): `GET /api/scale/queries` (the six, with SQL text), `POST /api/scale/run`
  `{query_id, engine, dataset}` → result + timing. Stream nothing; each run is ≤ a few seconds.
- Record a full table into `docs/SCALE.md` and `antar-frontend/public/lab/scale.json` via

## 16. References

- Chainey, Tompson & Uhlig (2008), the PAI; Hunt (2016) PEI / PEI*: PAI as area-normalised
  recall, reported as a curve. [Hu et al., arXiv 2006.00272](https://arxiv.org/abs/2006.00272v1) ·
  [Crime Science 2020 on PAI as Recall@k](https://doaj.org/article/de166f407ffd4357b558ccc27e0f379c)
- Conformal bands for LightGBM with count-type losses: locally weighted Pearson residuals gave
  nominal coverage with the narrowest bands ([arXiv 2507.06921](https://arxiv.org/abs/2507.06921v1)).
  Antar's GLM already uses Pearson-normalised Mondrian split-conformal; L3 reuses it.
- mlforecast conformal intervals need ≥ 2 CV windows and are often too narrow in practice
  ([Nixtla docs](https://nixtlaverse.nixtla.io/mlforecast/docs/how-to-guides/prediction_intervals));
  this plan therefore uses Antar's own calibration instead of adding mlforecast.
- LightGBM 4.x on PyPI ([pypi.org/project/lightgbm](https://pypi.org/project/lightgbm)):
  `pred_contrib=True` gives exact TreeSHAP contributions without the `shap` package.
- DuckDB reads SQLite files directly (`ATTACH … (TYPE sqlite)`) and Parquet natively
  ([DuckDB SQLite guide](https://duckdb.org/docs/current/guides/database_integration/sqlite.html)).
  L5 benchmarks Parquet (columnar) because that is the fair analytic comparison.
- Execution accuracy compares result sets, not SQL text, ignoring row order unless the question
  asks for an order ([arXiv 2602.21480](https://arxiv.org/pdf/2602.21480));
  gold labels themselves contain errors, so Antar writes its own truth
  ([BIRD gold-label errors](https://beancount.io/bean-labs/research-logs/2026/06/06/bird-benchmark-text-to-sql-real-database-gap)).
- Source plan with the full research table: `docs/DATATHON_FINAL_PLAN.md` §10.
